1. 문서 목적 및 시스템 구성 요소 개요

본 문서는 TrafficSync에서 데이터가 어떤 경로로, 어떤 형태로, 어느 타이밍에 흐르는지를 시나리오별로 기술한다. 개발자뿐 아니라 발표 검토자도 "신호 데이터가 어떻게 속도 정보와 합쳐지는가"를 이해할 수 있도록, 추상적 기호 대신 실제 테이블명·필드명·메서드명을 명시한다.

구성 요소설명
Spring Boot 백엔드 · :8080 REST API, WebSocket 브로드캐스트, 스케줄러(10초·60초·300초), Oracle DB 접근
Python AI 에이전트 · :8001 FastAPI + LangGraph ReAct 에이전트, MCP 도구 9개, Ollama 호출, SSE 스트리밍
React 프론트엔드 · :5173 카카오맵 렌더링, WebSocket 실시간 수신, AI 챗봇, CCTV 관제 (UTIC iframe)
Oracle Autonomous DB 교차로, 사용자, CCTV, 신호, 도로링크 매핑 영구 저장. Wallet 기반 TLS 연결.
Ollama LLM · :11434 qwen3:30b-a3b 로컬 모델. Python AI 서버만 호출. temperature=0.3, ctx=8192

외부 공공 API V2X(공공데이터포털), TOPIS 실시간 도로 소통 정보(상행/하행 속도), 기상청, 도로위험도, UTIC CCTV, VWorld 3D WebGL, 네이버 뉴스 검색, Groq LLM API, Google Cloud TTS [v1.1 수정 — T Data 삭제]

3. 핵심 매핑 구조 — 교차로 ↔ 도로 링크

TrafficSync의 핵심 과제 중 하나는 "교차로 ID"와 "도로 링크 ID"를 연결하는 것이다. V2X API는 교차로 단위로 신호를 주지만, TOPIS 속도 API와 도로위험도 API는 도로 링크(road link) 단위로 데이터를 제공한다. 이 두 세계를 잇는 매핑 테이블이 CROSSROAD_SUPPLEMENTAL_MAPPING이다.

왜 두 가지 링크 ID가 필요한가?
TOPIS 속도는 speed_link_id(링크 ID 문자열)로 조회하고, 도로위험도는 risk_line_string(LineString 좌표 쌍)으로 조회한다. 두 API의 조회 방식이 달라서 별도로 저장한다.
// CROSSROAD_SUPPLEMENTAL_MAPPING 한 행의 의미
교차로 ──────────────────────────────────────────────────────────
crsrd_id = "CR-001" // 교차로 고유 ID (CROSSROADS 테이블과 동일)

속도 매핑 (TOPIS API 호출용)
speed_link_id = "1620013200" // TOPIS linkId: 이 링크의 속도를 교차로 속도로 사용
speed_distance_meters = 87.3 // 교차로 중심 → 이 링크까지 거리(m)

위험도 매핑 (도로위험도 API 호출용)
risk_source_link_id = "1620013200" // 위험도 기준 링크 ID
risk_line_string = "LINESTRING(127.092 37.511, 127.093 37.512)" // 도로구간 좌표 (WGS84)
risk_distance_meters = 87.3 // 교차로 중심 → 이 링크까지 거리(m)
3.1 최초 매핑 계산 과정 (DB에 없을 때)

매핑이 DB에 없는 교차로가 있으면 CrossroadSupplementalMappingService.createNearestLinkMappings()가 실행된다.

최초 도로 링크 매핑 계산 절차
1
DB 조회
CROSSROAD_SUPPLEMENTAL_MAPPING 기존 매핑 로드
mappingRepository.findByCrsrdIdIn(crossroadIds) 로 현재 구의 교차로 전체 조회.
완전한 매핑(speed_link_id + risk_line_string 모두 있음)은 바로 캐시에 저장.
결과: 예) 전체 188개 중 → 178개 DB 매핑 있음, 10개 신규 계산 필요
▼ 매핑 없는 교차로만 아래 절차 진행
2
xlsx 로드
TOPIS 도로링크 기하 데이터 로드 (ROAD_LINKS 테이블 or xlsx)
TopisApiService.fetchAllLinkGeometries() — 서울 전체 도로링크의 LineString(시점좌표, 종점좌표) 로드.
이미 DB에 있으면 재사용. 없으면 xlsx 파일 파싱.
결과: Map<linkId, TopisLinkGeometry> — 수천 개의 링크 기하 데이터
3
최근접 계산
RoadLinkMappingService.mapCrossroadsToNearestLinks()
각 교차로 위경도(lat/lon)와 모든 링크의 시·종점 좌표 사이에서 Haversine 공식으로 최단거리를 계산. 가장 가까운 링크를 speed_link_id와 risk_source_link_id로 선택.
risk_line_string은 해당 링크의 시점·종점 좌표 2개를 LINESTRING으로 조립.
결과: Map<crsrdId, CrossroadRoadLinkMapping> — 10개 신규 매핑
4
DB 저장
CROSSROAD_SUPPLEMENTAL_MAPPING에 신규 행 INSERT
mappingRepository.saveAll() — 다음 구역 선택 시에는 DB에서 바로 재사용 가능. 계산 비용 절약.
5
메모리 캐시
mappingsByCrossroadId 갱신
SupplementalDataCacheService.updateMappings() — DB 재사용 178개 + 신규 10개 = 188개 전체를 메모리에 적재.
4. 시나리오 A — 구(區) 선택 시 전체 데이터 수집 흐름

사용자가 대시보드에서 특정 구(예: 강남구)를 클릭하면 fetch-area API가 호출된다. 이때 해당 구의 모든 교차로 데이터를 한 번에 수집하고 웹소켓으로 내보내는 전체 파이프라인이 실행된다.

시나리오 A — 구 선택 시 전체 수집 파이프라인
1
사용자 액션
프론트엔드: 구 선택 클릭
대시보드에서 구 이름 클릭 → POST /api/map/fetch-area { guName: "강남구" } 요청
2
DB 조회
CROSSROADS 테이블 — 해당 구 교차로 목록 조회
crossroadRepository.findByGuName("강남구") 실행
결과: List<CrossroadEntity> 예) 188개
필드: crsrd_id, crsrd_nm, lat, lon, gu_name
3
병렬 처리
V2X API 병렬 호출 (CompletableFuture)
188개 교차로를 동시에 V2X API에 요청. 각 교차로의 crsrdId를 URL 파라미터로 전달.
API URL: GET /api/its/signal?crsrdId={id}&apiKey=...
응답 필드: phase(현시번호), stage(위상), signalColor(Red/Green/Yellow/Left), remainTimeTenthSec(잔여시간 0.1초)
4
캐시 갱신
TrafficCacheService — signalCache에 V2X 신호 저장
updateAllSignals(newMap) — volatile 참조를 새 ConcurrentHashMap으로 원자적으로 교체. 이 시점에는 속도·위험도 없음.
signalCache: { "CR-001" → TrafficStatus(crsrdId, lat, lon, phases[], …), … }
5
매핑 로드/계산
도로 링크 매핑 — DB 재사용 or 새로 계산 (3장 참조)
188개 교차로에 대해 CROSSROAD_SUPPLEMENTAL_MAPPING 확인.
· 매핑 있는 교차로(178개): DB에서 speed_link_id, risk_line_string 바로 로드
· 매핑 없는 교차로(10개): TOPIS xlsx + Haversine 계산 → DB 저장 후 로드
mappingsByCrossroadId: { "CR-001" → { speedLinkId:"1620013200", riskLineString:"LINESTRING(…)" }, … }
6
외부 API
TOPIS 속도 API 병렬 호출 (최대 4개 동시)
mappingsByCrossroadId에서 중복 제거된 speed_link_id 목록 추출 → 각 linkId별 TOPIS API 호출
API URL: GET /api/topis/speed?linkId={id}&apiKey=...
응답: { linkId, speedKph, travelTimeSec }
저장: speedsByLinkId["1620013200"] = RoadSpeedSnapshot(speedKph=35.2, …)
7
외부 API
도로위험도 API 병렬 호출 (최대 4개 동시)
mappingsByCrossroadId에서 risk_line_string 목록 추출 → 각 LineString별 도로위험도 API 호출
API URL: GET /api/roadrisk?lineString={wkt}&apiKey=...
응답: { riskIndex(0~100), riskGrade("높음") }
저장: risksByLinkId["LINESTRING(…)"] = RoadRiskSnapshot(riskIndex=72, riskGrade="높음")
8
데이터 합산
enrich() — V2X 신호에 속도·위험도·기상 합산
188개 TrafficStatus 각각에 대해 (9장 상세 설명):
· speedsByLinkId[speedLinkId] 에서 speedKph, travelTimeSec 읽어 set
· risksByLinkId[riskLineString] 에서 riskIndex, riskGrade 읽어 set
· weather 캐시에서 기온·강수·풍속 set
· speedKph 기준으로 congestion 재계산 (speed<20→혼잡, <40→서행, else→원활)
결과: TrafficStatus { crsrdId, phases[], speedKph:35.2, riskGrade:"높음", congestion:"서행", weather:{temp:21}, … }
9
WebSocket
TrafficWebSocketHandler.broadcast() — 전체 브라우저에 전송
wsSessions(CopyOnWriteArrayList)의 모든 세션에 JSON 직렬화된 TrafficStatus[] 전송.
실패 세션(연결 끊김)은 리스트에서 자동 제거.
10
프론트엔드
React — wsData 상태 갱신 → 화면 리렌더링
ws://localhost:8080/ws/traffic에서 JSON 수신 → setWsData() 호출
지도 마커 색상(신호색), 사이드바 병목 목록, 위험 교차로 목록 자동 업데이트
5. 시나리오 B — 10초 정기 폴링 (상시 운영)

앱이 동작하는 동안 TrafficScheduler.pollTrafficData()가 10초마다 실행된다. 구 선택 시(시나리오 A)와 달리 속도·위험도·매핑은 각자의 주기로 따로 갱신되므로, 폴링은 V2X 신호만 새로 가져와 기존 캐시와 합산한다.

시나리오 B — 10초 정기 폴링
1
조건 확인
areaRefreshInProgress 플래그 확인
구 선택(시나리오 A)이 진행 중이면 이번 폴링 건너뜀 → 중간 상태 덮어쓰기 방지
2
DB 조회
현재 중심 좌표(lat/lon/radius) 기준 반경 내 교차로 조회
crossroadRepository.findWithinRadius(centerLat, centerLon, radiusKm)
기본값: 잠실 좌표 반경 1km. 구 선택 시 좌표 업데이트됨.
결과: List<CrossroadEntity> N개
3
외부 API
V2X API 병렬 호출 → 최신 신호 데이터 수신
빈 결과(타임아웃 등) 반환 시 기존 캐시 유지하고 폴링 건너뜀
signalColor, remainTimeTenthSec, phase, stage 갱신
4
채워넣기
enrichTrafficStatuses() — 방금 받은 V2X 신호 객체에 속도·위험도·기상 set()
V2X 폴링은 신호 데이터만 새로 받는다. 속도·위험도·기상은 각자의 스케줄러가 별도로 메모리 캐시를 갱신하고 있으며, enrich()는 그 캐시에서 값을 읽어 TrafficStatus에 set()만 한다. 새로 계산하거나 API를 추가로 호출하지 않는다.

· speedsByLinkId[speedLinkId] 읽어서 → status.setSpeedKph()
· risksByLinkId[riskLineString] 읽어서 → status.setRiskGrade()
· weather 읽어서 → status.setWeather()
※ 속도는 최대 59초, 위험도는 최대 299초, 기상은 최대 599초 된 캐시값일 수 있음 (stale=true로 표시)
5
WebSocket
broadcast() — 전체 브라우저에 갱신된 데이터 전송
6. 시나리오 C — 60초 TOPIS 속도 갱신
시나리오 C — SupplementalDataScheduler.refreshRoadSpeeds() (60초)
1
캐시 참조
mappingsByCrossroadId에서 speed_link_id 목록 추출
188개 교차로 매핑에서 speedLinkId만 모아 중복 제거 → 조회할 linkId Set
예) { "1620013200", "1620014100", "1620015300", … } — 수백 개 고유 linkId
2
외부 API
TOPIS 속도 API 병렬 호출 (최대 4개 동시, 타임아웃 12초)
각 linkId별 TOPIS REST API 호출. 12초 타임아웃 초과 시 남은 요청 취소(cancelled).
응답: { linkId, speedKph:45.0, travelTimeSec:12 }
저장: speedsByLinkId["1620013200"] → RoadSpeedSnapshot 갱신

11. enrich() 합산 로직 상세

SupplementalDataCacheService.enrichTrafficStatus()는 V2X 신호만 있는 TrafficStatus에 속도·위험도·기상을 채워넣는 핵심 메서드다.

소스: speedsByLinkId 캐시
속도 (speedKph)
mapping = mappingsByCrossroadId[crsrdId]
linkId = mapping.speedLinkId
speed = speedsByLinkId[linkId]
status.speedKph = speed.speedKph
없으면 → speedStale = true
소스: risksByLinkId 캐시
위험도 (riskGrade/Score)
key = mapping.riskLineString
or mapping.linkId
risk = risksByLinkId[key]
status.riskIndex = risk.riskIndex
status.riskGrade = risk.riskGrade
없으면 → riskStale = true
소스: weather 캐시
기상 (weather)
weather = this.weather (공유)
status.weather = weather
baseDateTime 포함
없으면 → null
congestion 계산 규칙
조건결과비고
speedKph < 20혼잡TOPIS 속도 기반 (우선)
speedKph < 40서행TOPIS 속도 기반 (우선)
speedKph ≥ 40원활TOPIS 속도 기반 (우선)
speedKph 없음 + 평균 적신호 대기 > 60초혼잡V2X 신호 잔여시간 기반 (fallback)
speedKph 없음 + 평균 적신호 대기 > 30초서행V2X 신호 잔여시간 기반 (fallback)
speedKph 없음 + 나머지원활V2X 신호 잔여시간 기반 (fallback)
stale 플래그: 속도·위험도 API 호출이 실패하거나 아직 수집 전이면 해당 필드는 stale=true로 표시된다. 프론트엔드에서 이를 읽어 "데이터 없음" 또는 회색 표시로 처리할 수 있다.
